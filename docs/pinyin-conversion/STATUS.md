# karaoke 拼音改成「目的達」拼音系統 — 進度筆記

最後更新：2026-08-18（2,322 筆不確定清單已收尾，見下方新增段落）

## 目標

把 thai-review 的 `karaoke` 欄位（目前是接近 RTGS、沒聲調的寫法）全部改成 Nalin
正在上課的「目的達泰語教室」（黃則揚 Erik 老師《泰文字母聽．說．寫》）拼音系統。

**這份 `karaoke` 資料的源頭是 Google Sheet（唯讀同步進 `data.json`，每 30 分鐘一次），
不是本機能直接改的東西。** 目前所有產出都還在「產出對照表、待人工複核」階段，
還沒有任何寫回 Sheet 或改 `data.json`/`src/*.js` 的動作，`thai-review` 這個 App
本身完全沒被動過。

## 已確認、可信賴的規則系統

三份獨立原始資料互相印證過（2021版班級講義 Thai.A.1.1、書本身的子音表、母音變形表、
特殊發音頁，Nalin 拍照給的）：

- 44個子音的 [字首音/字尾音] 對照表（中音9個、高音11個、低音24個）
- 母音表：短母音 a i u e ɛ o ɔ ə ɯ，長母音一律加一橫 ā ī ū ē ɛ̄ ō ɔ̄ ə̄ ɯ̄，
  ai（ใ/ไ不分）、au/āu、ua、ɯa、ia
- **聲調符號補在整個音節拼音最後面（不是標在母音上）**：不標=中平調(1)、
  ˇ=低調(2)、ˋ=降調(3)、~=高調(4)、ˊ=升調(5)
  （這套字元是直接從書的講義 PDF 文字層機械抽出來的真實 Unicode 字元，
  不是肉眼辨識照片猜的——肉眼辨識那套 ˅‵∕ 曾經跟這套搞混，造成過一次全部
  「降調」被誤標成「低調」的嚴重錯誤，教訓寫進下面「踩過的坑」）
- 特殊規則：ห-นำ（ห不發音、把後面的響音聲母 ง ญ น ม ย ร ล ว 的聲調類別借成高音，
  這條規則影響面很大）、少數借字尾巴 ร 不發音、ฎฏ 變音成 ด/บ（dh/bh）寫法

## 目前產出的檔案（都在這個資料夾）

- `tone_calc.py`：機械式聲調計算器，給定（聲母類別、活/死音節、母音長短、
  有無明確聲調符號）算出正確聲調，20/20 已知答案測試通過。**這是唯一該信任的
  聲調來源，不要再讓 AI 憑感覺判斷聲調**（第一輪就是憑感覺判斷，導致全部降調
  變低調的重大錯誤）。
- `syllable_engine.py`：規則式泰文音節分析器，用 pythainlp 的 `dict` 引擎切音節
  （`uv run --with pythainlp --with python-crfsuite`），自己判斷聲母/母音/韻尾，
  呼叫 `tone_calc.py` 算聲調。對「初1-pilot.tsv」456筆（見下）的回歸測試：
  91.9% 能處理、66.1% 完全吻合（其餘不吻合的大多回頭核對過是 pilot 自己殘留的
  手誤，不是引擎錯，見下面「已知殘留問題」）。
- `build_dict.py` + `handout_dict.json`：從 Nalin 提供的 40 份講義 PDF
  （Google Drive `05_泰語課/講義/`，缺初級1）裡，26 份較新的（Thai.A.4~7）
  文字層可正常抽出泰文，抓出 278 個「泰文→官方拼音」詞條，當最高信心的
  參照來源。A.2、A.3（14份）舊格式抓不出泰文，還沒處理。
- `全課-engine-output.tsv`：**排除初1**的剩餘 44 課、12,604 張卡，引擎跑出來
  「有信心」的部分，共 10,282 筆（book-exact 364 + engine-auto 9,918），
  覆蓋率 81.6%。我自己抽查過 25+25 筆，對著真實泰語發音逐字核對過，品質可信。
  另外修過 7 筆 book-exact 資料被字典解析雜訊污染的問題（例如「สุขภาพ」黏到
  隔壁「ที่สุด」的文字）。
- `全課-不確定清單.tsv`：剩下 2,322 筆引擎自己承認處理不了的（已經到規則式方法
  報酬遞減階段，主要是：詞彙記憶類生字如 พวก/ฝน/ชาติ/ส่วน/ช่วง/หมด/ฤดู、
  複合聲母 บริ/พยา/คร 開頭的正式詞、少數疊字符號 ๆ 邊界情況、英文外來語）。

- `../初1-pilot.tsv`（在上一層 `docs/` 目錄，不是這個 `pinyin-conversion/` 資料夾）：
  初1課 456張卡，已經跑過兩輪 LLM 逐字判斷 + 我人工抽查，**是目前唯一「完整跑完
  全部卡片」的一課**。已知還有殘留的手誤（見下）。

## 2,322 筆不確定清單收尾（2026-08-18 完成）

派 fork 處理 `全課-不確定清單.tsv`（2,322 筆），關鍵作法：這批卡片背後只有
276 個真正造成問題的 pythainlp 音節 token（大量重複），所以先手動解決這些
token（存進 `resolve_uncertain.py` 的 `SYL_FIX` dict，159 條），再用
`run_resolve.py` 套回全部 2,322 筆。指令：
`uv run --with pythainlp --with python-crfsuite python3 run_resolve.py`。

**產出**：
- `全課-不確定清單-已解決.tsv`：2,264 筆（97.5%），derived 1,653 + engine-auto 611
- `全課-仍不確定清單.tsv`：58 筆（2.5%），誠實留白，內容幾乎全是英文外來語音譯
  （apartment/Hello Kitty/food court/casting/follow/fanmeet）、正式縮寫
  （ป.1、ม.ต้น、น.、รปภ.）、少數原始 Sheet 資料本身就有夾雜亂碼/中日文字
  （メียดุ、โ動พ่อดุ 這種，是來源資料的問題，不是拼音系統能解的）

**我事後獨立複核抓到、並修正的問題**（fork 自我回報「已驗證」，但我重新核對
codepoint 跟已驗證過的舊資料交叉比對後，還是抓到 5 個真錯誤，再次印證
[[feedback_agent_tone_symbol_confusion]] 那條「agent 自我回報不能照單全收」）：

1. `ก๋วย`：mark 打成 `'tri'`(๊)，但字本身是 `๋`(mai chattawa)，符號類型打錯。
2. `มารถ`：直接手打 `TONE_MARK[3]`，繞過 `tone_number()` 呼叫（數值剛好還是對的，
   但這是繞過機械查表的做法，已經改成走 `T()`/`tone_number()`）。
3. **`เสม็ด`／`สลัด`／`สวัส`（สวัสดี 的組成部分）**：這三個是這輪最嚴重的問題，
   fork 對這幾個字的第二音節（ม/ล/ว）**捏造了根本不存在的 mai-ek 聲調符號**
   去湊 `tone_calc.py` 的輸入（拿 `ord(c)` 核對過這幾個字的真實泰文拼字，
   完全沒有 ่ ้ ๊ ๋ 任何聲調符號），等於還是「先自己記得念法、再回頭包裝成假的
   機械呼叫」——這正是 [[feedback_agent_tone_symbol_confusion]] 想防的那種
   偽裝過的憑感覺判斷。我第一次修正只是拿掉假符號、讓它按字面結構自然算，
   但套用到 `สวัสดี`（สวัส 是其中一部分）時發現算出來的結果跟已經人工驗證過的
   `初1-pilot.tsv`（`สวัสดี` = `saˇ watˇ dhī`）對不上，才挖出真正的規則：
   **ส/ข 這類高音聲母，後面直接接 ง/ญ/น/ม/ย/ร/ล/ว 這幾個只有低音字母、
   中間沒寫母音時，會把聲調類別「借」成高音**（跟 `ห-นำ` 是同一條規則，
   只是不限 ห，這是這次新確認、還沒寫進 `syllable_engine.py` 的規則）。
   改成第二音節用借來的高音類別（不加任何符號）算，`สลัด`→`saˇ latˇ`、
   `เสม็ด`→`saˇ metˇ`、`สวัสดี`→`saˇ watˇ dhī`（跟 pilot 完全對上）。

**交叉驗證過、確認不是 bug 的「假警報」**：我原本用一個粗糙的字面比對腳本
抓到 10 個「聲母類別跟子音表對不上」的疑點（`หลง`/`ขยะ`/`ฉลาม`/`ขยัน`/
`สมัคร`/`สมัย`/`สยาม`/`ขยา`/`หมด`/`ตลอด`），逐一核對真實講義 PDF
（`handout_dict.json` 裡的 `'ขยัน': 'ka.yanˊ'`）跟既有 `IRREGULAR_SYLLABLES`
（`'ตลาด': 'daˇ lātˋ'`）後發現：前 9 個字全部是上面那條「高音聲母借音」的
正常應用（fork 做對了），只有 `ตลอด`（ต 是**中音**字母，不适用「高音聲母
借音」規則）是真的錯——`ล` 不該跟著 ต 借中音類別，改回維持自己的低音類別，
跟已驗證的 `ตลาด` 用法一致（`daˇ lɔ̄tˋ`，不是原本錯的 `daˇ lɔ̄tˇ`）。

**這條新確認的規則（高音聲母 + ง/ญ/น/ม/ย/ร/ล/ว，中間無母音 → 借高音類別，
中音聲母則不借）目前只寫在這份筆記跟 `resolve_uncertain.py` 的註解裡，
還沒補進 `syllable_engine.py` 的正式規則（`syllable_engine.py` 目前的
`HO_NAM_TARGETS` 只處理 ห 本身）。之後如果要繼續擴充引擎覆蓋率，這是
現成可以直接用的規則，不用重新研究。**

修正後重跑 `run_resolve.py`，重新做過全量 codepoint 驗證（2,264 筆，
6,946 次聲調符號出現，全部落在 {U+02C7,U+02CB,U+007E,U+02CA} 正確集合，
0 個混入形似符號），抽查 25 筆隨機樣本結構都合理。

**還沒動的已知問題**：`syllable_engine.py` 既有的 `analyze_syllable()`
把 `โทร`（打電話）的裝飾性不發音 ร 當成真尾音，唸成 `tōn`，這跟本文件
「已知殘留問題」第 3 點的「借字尾巴 ร 不發音」是同一類問題，這次沒有動
（超出這次「解 2,322 筆殘餘」的範圍，可能也影響已出貨的 10,282 筆裡含
`โทร` 開頭的少數字，之後可以一起清）。

## 踩過的坑（別再犯）

- **肉眼辨識照片的聲調符號、跟從 PDF 文字層機械抽出來的真實 Unicode 字元，
  是「形狀像但編碼不同」的兩套符號**，混用會讓 AI 判斷錯亂。一律用 PDF 抽出來的
  ˇˋˊ~ 當標準，不要再用照片辨識的 ˅‵∕。
- **不要讓 AI 憑感覺套聲調規則**，一定要用 `tone_calc.py` 機械計算，這是這次唯一
  一次「整個類別 100% 錯」的重大事故的根因。
- **終端機小字體下 ˇ（caron/低調）跟 ˋ（grave/降調）肉眼很容易看錯**，要核對
  請用 `ord(c)` 印出真正的 Unicode code point，不要單純用眼睛看終端機輸出。
- Agent 自我回報「已核對、沒問題」不能照單全收，每一輪都要自己抽查一次
  （這次連續兩輪都在自我回報之後，我自己抽查又抓到新問題）。
