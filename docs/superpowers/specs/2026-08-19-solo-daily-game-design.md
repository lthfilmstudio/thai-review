## 1. 產品定位

清心安神是一個給 Nalin 自己使用的泰語練功 App。

核心承諾：

> 每天打開，就知道下一步；完成一小局，就算今天有來。

它不是多人社群，也不追求內容最多。它要把 Nalin 正在上的課、老師音檔、SRS 複習和生活對話，組成一條可以每天走一小步的個人練習路線。

### 要解決的真實痛點

Nalin 自述的兩個問題，決定了這份設計的優先順序：

1. **常常忘了每天要練習** → 缺**提示（trigger）**。這跟 App 裡面做得多好玩無關，因為沒打開就看不到。
2. **沒有主動打開的慾望** → 缺**期待感**。

所以本設計分成兩個層次，且**第一層優先於第二層**：

```text
第一層：讓她想起來、願意打開   → 第 5 節（提醒與回訪）、第 6 節（streak 規則）
第二層：打開之後值得做完一局   → 第 4 節（遊戲局）、第 9 節（回饋層）
```

## 2. 設計原則

1. **單人優先**：所有分數、streak、徽章和進度都只跟自己的過去比較。
2. **遊戲與任務同一件事**：首頁的每日任務就是遊戲中的一小局，不做一個孤立的遊戲入口。
3. **不設時間目標**：不要求每天 7 分鐘或固定分鐘數；只記錄今天實際累積多久。
4. **低決策成本**：首頁直接給下一局，不要求每天重新挑課、挑模式。
5. **課程優先，但不排擠 SRS**：新內容以最新一堂課（目前為「中 2-4」）為主；但複習局要跨所有課程取到期卡，最新一堂只加權優先，否則舊課的到期卡會被餓死（見第 8 節）。
6. **溫和的遊戲化**：可以有連擊、戰績、徽章和安神保護，但不使用扣心、懲罰、付費貨幣或倒數壓力。
7. **保留現有資產**：優先使用現有 Sheet、`data.json`、老師音檔、中文提示音、SRS 和 `src/achievements.js`，不先引入新的付費 AI。
8. **App 主動來找人，不是等人想起來**：提醒是這個產品的基礎建設，不是附加功能；而且提醒本身要帶內容、有價值，不是純催促。

## 4. 每日任務與遊戲局

### 第 1 局：聲音熱身／音感挑戰

- 來源：本週課程（含總複習）中還沒接觸過的新卡優先，湊不滿 5 句再從已學過的卡補。刻意不抓 SRS 到期／弱卡——那是第 2 局的工作，避免兩局考到同一批卡。
- 玩法：
  1. 開始自動播放一次老師泰文音（沿用現有 baked TTS 音檔，不新增資產），畫面顯示「🔁 重聽」+ 4 個中文意思選項。
  2. 正解 + 3 個干擾項；干擾項從同一批候選卡（同課字彙）隨機抽，不做語意相似度運算，維持純函式、零依賴、好測試。
  3. 選完立即回饋：對→綠色打勾；錯→紅色叉、正解泰文卡片浮現（含目的達拼音）、可立刻重聽正解音檔。不管對錯都能點「下一句」，不卡關、不強迫訂正。
  4. 跟讀：第一版沒有麥克風／語音辨識（Phase 5 才做），播完老師音後顯示「你可以跟著唸一次」+ 短暫空拍即可進下一句，純儀式感，不接收也不評分使用者的聲音。
- 完成條件：完成 5 句，不要求全對。
- 結果：顯示「5 句中對了 N 句」+ 需要再聽的句子清單（答錯那幾句，可逐句重播）+ 重聽按鈕，不給等第或分數評語，直接進下一局按鈕。

### 第 2 局：複習容易忘的字／連擊複習

- 來源：**跨所有課程**的 SRS 到期／答錯／ease factor 偏低卡 6 張，最新一堂加權優先（理由見第 8 節）。
- 玩法：一張一張答題，答對形成連擊；答錯可立即重看與重播。
- 完成條件：走完 6 張卡。
- 結果：顯示本局連擊、答對率和「下次複習」安排。

### 第 3 局：生活對話／情境選答

- 玩法：一個完整情境，兩人來回共 6 句，每人各講 3 句。
- 完成條件：完成整組對話，不是只練單句。
- 結果：顯示情境完成度、可重播整段，以及再挑一次的入口。

**資料契約（2026-08-20 拍板：C 案，AI 初稿 + 人工審核 + 存進 Sheet）**

初稿寫「來源：本週課程的生活句與對話素材」，但核實後**這種素材並不存在**：Sheet 的課程資料沒有 `speaker`、`turn`、`dialogue id` 任何一種欄位，卡片是獨立的單字／句子。現有的「對話」mode（`src/dialog.js`）是**抽 6 個單字丟給 worker `/dialog`，由 Gemini 即時生成 5–8 turn**（`src/dialog.js:1-2`、`:11`），句子不落地；播放走 `speakCard({thai})` 即時合成（`:203`），**沒有 baked 老師音**。

考慮過三條路，選 C：

| | 做法 | 判斷 |
|---|---|---|
| A | 沿用既有 AI 即時生成，改成固定 6 句 3:3 | 工作量近乎零，但**永久**帶著：唯一需要連網的一局、練完就不見不能重複練、沒有 baked 老師音、每次換組都花 API、內容可能超出當前程度 |
| B | 全手寫對話進 Sheet | 好處齊全，但 Nalin 還在學泰文，從零寫 6 句對話負擔最重 |
| **C** | **AI 生成初稿 → 人工審核挑掉不自然／過難的 → 存進 Sheet** ← **採用** | 用**一次性的審核工作**換掉**永久的網路依賴與 API 成本**；落地後完全走 B 的路徑 |

C 案的實作要點：

- **素材產出是一次性離線工作，不是 App 功能**：AI 一次生成約 10 組情境對話 → Nalin（或老師）審核 → 貼進 Sheet 新分頁。之後 App 端完全不呼叫 AI。
- **Sheet 新分頁欄位**：情境 ID／情境名稱／順序（1-6）／說話者（A|B）／泰文／目的達拼音／中文。要同步改 `scripts/sync-sheet.py` 與 `src/data.js` 的欄位對應（**注意兩邊都是靠表頭文字完全比對，改表頭前要先看 COL_ALIASES**）。
- **音檔可預烤**：對話句進 Sheet 之後就走跟單字卡同一套 baked 音檔流程，這局因此能離線播老師音。
- **審核標準**：只用老師教過的句型與當前程度可理解的詞；不自然、太長、超綱的直接砍掉不改。寧可 10 組砍到剩 6 組，也不要留半生不熟的素材。
- 現有的 AI 即時對話 mode **保留不動**（它是另一個功能），這局不共用那條路徑。

## 5. 提醒與回訪（Trigger 層）

**這一節是整份設計的最高優先項**，因為「忘了打開」是 Nalin 的第一痛點，而 App 內的所有設計都是打開之後才生效的。

參考依據：Duolingo 團隊自述，iOS 桌面 widget（一個被動、永遠看得到的提示）讓使用者投入度提升約 60%；撐過 7 天連續的使用者隔天回訪率是 2.4 倍。他們最強的留存機制不是遊戲本身，是「讓你一直看得到它」。

### 5.1 技術前提（已查證）

- **Web 標準沒有本機排程通知**。不能像原生 App 那樣在裝置上設定「每天 9 點提醒自己」，一定要有伺服器在對的時間推 Web Push。
- **Nalin 是 Android Chrome PWA**，Web Push 支援成熟完整（iOS 限制多很多，剛好不受影響）。
- **Badging API（`navigator.setAppBadge`）在 Chrome for Android 不支援**，不能用它做「圖示上顯示今天幾張待複習」。**Android 上唯一能讓 PWA 圖示長出紅點的方法，是有一則未讀通知。** 所以 Web Push 不只是提醒，它同時是這個 App 在 Android 上唯一拿得到的「Duolingo widget 效果」。

### 5.2 兩條實作路線

| | A. Web Push（CF Worker + VAPID + Cron Trigger） | B. Telegram bot 每日一則 |
|---|---|---|
| 點下去 | 直接進 App | 進 Telegram，要再點連結 |
| 圖示紅點 | 有（Android 未讀通知自動帶） | 無 |
| 要建的東西 | 訂閱流程、VAPID 金鑰、Worker 推送邏輯、排程 | 幾乎沒有，已有多支 bot 在跑 |
| 現有資產 | 需要開一支**獨立**新 Worker（第 12 節安全契約：不併進持有 GCP key 的 `lth-tts-proxy`） | 既有 Telegram bot 群 |

**分段走（已定案）**：**Phase 0.5 先用 B（Telegram）**——幾乎不用建東西、跟 App 完全解耦，先花 14 天驗證「有提醒就真的會打開」這個假設；**方向性訊號與 Nalin 自評支持繼續投資，才做 A（Web Push）**（Phase 4）拿圖示紅點與一鍵進 App（判斷法見 13 節 Phase 0.5，沒有自動通過的數字門檻）。這不是二選一，是先後順序：先用最便宜的方式證明假設，再決定要不要付工程成本。

### 5.3 通知內容設計（比通知本身更重要）

研究結論很明確：一般的「來練習吧」會被直接滑掉。**通知要帶今天的內容，本身就有價值。**

- **每日提醒**（固定時間，時間可設定）：把「今日一句」的泰文本文 + 中文意思放進通知本文，末尾附 App 連結。這樣就算沒點進去，光看通知也學到一句；同時製造期待感（下一則會是哪句？）。
  - ⚠️ **通知裡不能放「今天有 N 張到期」**：SRS 進度只活在瀏覽器 localStorage 的 `state.progress`（`src/state.js:156`），而且經核實**沒有任何外送路徑**——沒有 server 同步、沒有上傳。外部的 Telegram bot 或 Cloudflare Worker 拿不到這個數字。到期張數只能留在 App 首頁顯示。要讓通知帶到期數，前提是先做「進度上傳」，那是另一個等級的工程（隱私、認證、衝突處理），第一版不做。
  - **今日一句的資料來源（實作時再簡化一層，2026-08-20）**：App 本體在 Cloudflare Access 後面，外部抓不到線上那份 `data.json`。但 `data.json` 本身是**明文 commit 進這個 repo**的靜態檔（`sync-sheet.py` 每 30 分鐘更新），GitHub Actions checkout 這個 repo 時就直接讀得到——**不用另外重讀 Sheet**，比原設計少一次網路請求跟一份重複的解析邏輯。實作見 `scripts/daily-reminder.py` + `.github/workflows/daily-reminder.yml`。
  - **挑句規則（2026-08-20 修正，原「`type` 非 `word`」規則有 bug）**：初稿寫「跳過 `type` 是 `word` 的」，但核實 `data.json` 發現**「中 2-4」296 張卡的 `type` 100% 是 `word`**，而且 `sync-sheet.py:139` 缺欄位時本來就預設成 `"word"`——照原規則篩，最新這堂課會**一句都選不出來**。改成純長度門檻：**泰文字元數 ≥ 15** 才算整句（該堂課中位數 13、105/296 張達標，門檻可用）。`type` 欄位不可靠，不當篩選依據。
- **新課事件**：Sheet 同步（現有 GitHub Action 每 30 分鐘跑）偵測到新分頁時推「這週的新課上了，X 個新句子」。事件驅動比每天固定嘮叨有力得多，因為真的有新東西。這也正是這個 App 對 Duolingo 的獨特優勢——**內容是這禮拜老師剛教的，不是通用教材**。
- **里程碑**：連續 7 / 30 / 100 天達成時推一則慶祝。

### 5.4 節制原則

- 一天最多 **1 則**常規提醒；新課／里程碑事件另計，但同一天總數不超過 2 則。
- 不推純催促、不推連續多則、不在深夜推。
  - Phase 0.5 定的 **22:00** 是 Nalin 2026-08-20 明確拍板的時段（見第 16 節第 17 項），不算違反這條——22:00 在多數人的作息裡還不到「深夜」，且是本人親自選的固定時間，不是系統自動排的深夜推播。這條原則主要是防未來 Web Push 或事件通知自動選到不合理的時間點。
- Chrome 對推播的頻率限制與濫發防護持續在收緊，維持低頻率也是為了不被系統降權。

## 6. streak 與安神保護規則

計畫書原本只畫了「連續天數」和「安神保護」的畫面，沒有定義規則。以下是完整規則，設計上刻意**比直覺更寬鬆**——因為斷了 streak 之後直接棄用 App，是這類產品最主要的流失原因。

- **完成 1 局 = 今天有來，streak +1。** 3 局是加分，不是門檻。首頁「今日挑戰 1 / 3」的文案要讓這件事一眼看得出來，不能讀起來像非做滿 3 局不可。
  - ✅ **已解決**：這條原本跟第 7 節「遊戲不寫 SRS grade」互相矛盾（`streakDays()` 判定依據 `reviewed`，而遊戲不會加 `reviewed`）。解法是每日日誌加 `games` 欄位、`streakDays()` 判定放寬成 `reviewed > 0 || games > 0`，完整設計見 **第 11.3 節**，實作時直接照那節做，這裡不再是待解的 blocker。
- **安神保護上限 2 個**（不是 1 個）。Duolingo 實測從 1 個放寬到 2 個，日活留存與回訪率有顯著提升。斷天時自動消耗 1 個。
- **回補規則**：每連續 7 天回補 1 個，上限仍是 2 個。
- **補救昨天**：斷天的隔天打開 App，可以用「今天多完成 1 局（共 2 局）」把昨天補回來。代價是多練一局，不是假的付費貨幣——跟產品目標一致，也符合「不使用付費貨幣」原則。
- **里程碑慶祝**：7 / 30 / 100 天。**7 天要特別做**，那是留存的懸崖點。
- 這整套跟「溫和的遊戲化」原則一致：業界研究直接點名「用扣心、能量限制擋人練習，把 streak 焦慮擺在能力成長前面」屬於操縱式設計，本專案明確不做。

### 6.1 結算順序（每次開 App 時跑一次）

「自動消耗保護」跟「補救昨天」會同時具備觸發條件，必須定死誰先，否則會出現扣了保護又要她補做一局的雙重懲罰。順序如下：

```text
開 App
 └→ 算出「上次有來」到今天中間斷了幾天 D
     ├─ D = 0 → 什麼都不做
     ├─ D ≥ 1 → 先自動消耗安神保護，一天扣一個，最多扣到保護歸零
     │           扣得完（D ≤ 手上保護數）→ streak 續，提示「用掉 N 個安神保護」，結束
     └─ 扣不完（還差 R 天沒補）→ 進補救判定
         ├─ R = 1 → 提供「今天多完成 1 局（共 2 局）補回昨天」的入口，
         │           在她完成第 2 局之前 streak 先顯示為斷、不先歸零
         └─ R ≥ 2 → streak 歸零，不提供補救（斷太久就重新開始，不做無限回溯）
```

配套規則：

- **保護優先於補救**，而且兩者不重複計費：已經用保護補掉的那天，不會再要求多做一局。
- **補救只補最近 1 天**，且一天只能補一次；補成功後不回補保護。
- **保護回補**：每連續 7 天回補 1 個，上限 2 個。回補的計數以「連續天數」為準，用掉保護的那天仍算連續（不然回補永遠追不上消耗）。
- **多天沒開的下限保護**：不管斷多久，`progress` 與成就都不會被清掉，歸零的只有 streak 數字。

### 6.2 遊戲日在月曆怎麼顯示

現有月曆熱度吃的是每日日誌的 `reviewed`（正式 SRS 評分次數）。加了 11.3 的 `games` 欄位之後會出現矛盾：**只玩遊戲沒評分的那天，streak 有算，月曆卻是空白格。**

處理方式：月曆同時吃兩個欄位，但視覺上分得出來——

- **有 `reviewed`**：實心色塊，深淺照現有 `heatLevel()` 的張數分級。
- **只有 `games`**：同色但用描邊／淡底，代表「有來，但沒做正式複習」。
- 兩者都有：照 `reviewed` 的實心色塊處理。

這樣「有來」跟「複習了幾張」兩件事在同一張月曆上都讀得出來，也不會讓遊戲日看起來像沒來過。

## 7. 今日挑戰與 SRS 的關係

遊戲結果和 SRS 資料要分層處理：

```text
遊戲答題結果 → 本局戰績／今日進度
                         └→ 使用者確認後，才寫入 SRS grade
```

原因：同一張卡在遊戲裡答錯，不應該因為一次小遊戲就被過度懲罰；SRS 的「重來／有點難／可以／很熟」仍由正式複習結果決定。

第一版可以先保留現有評分流程，遊戲只記錄戰績；第二版再評估把穩定的答題結果映射到 SRS。

> 名詞說明：SRS grade 指 `src/srs.js` 的四檔評分（`again` 重來 / `hard` 有點難 / `good` 可以 / `easy` 很熟），會寫進 `state.progress`，決定該卡的 `nextReviewAt`（下次複習時間）與 `easeFactor`（間隔成長速度）。

## 8. 個人化出題規則（第一版）

第 2 局／連擊複習的選卡範圍是**所有課程**，不限本週：

1. **全部課程**今天到期的 SRS 卡（`getDueCards()` 已有，`src/srs.js:67`）。
2. 全部課程中近期答錯／ease factor 偏低的卡。
3. 最新一堂課的卡只是**加權優先**，不是唯一來源。
4. 前三項湊不滿才補最新課尚未接觸的新卡。
5. 補足固定數量，避免每天內容太少。

**為什麼不鎖在最新一堂**（初稿的寫法，已修正）：SRS 的價值就在於把幾週前學的東西在快忘記時撈回來。只抓最新一課會讓舊課的到期卡永遠排不進來、被活活餓死；再加上第 7 節決定「遊戲不寫 SRS grade」，這些卡的 `nextReviewAt` 不會前進，於是**連續好幾天都抽到同一批卡**。現有的「今日」mode 本來就在做跨課程 due 彙整（`today.js`），這裡是沿用既有能力，不是新工程。

第 1 局／音感挑戰選卡邏輯相反：優先抓該課尚未接觸的新卡，湊不滿再補已學過的卡，刻意不碰 SRS 到期／弱卡，避免跟第 2 局撞同一批卡（詳見第 4 節）。

「最新一堂」＝資料清單中最後一堂課程，**含總複習**；若未來 Sheet 排序規則改變，再加一個單人設定讓 Nalin 手動指定本週課程。

## 9. 遊戲回饋層

每局都要有三段回饋：

```text
開始前：這一局要做什麼
進行中：目前答對幾題／連擊幾次／還剩幾張
結束後：本局結果／需要再練的內容／下一局
```

避免只顯示「完成」；使用者要知道自己哪裡變好了、下一次該從哪裡接續。

### 9.1 成就徽章（既有系統，已經接好了）

**這套系統不只寫好了，而且已經完整接進現有 App 在跑**——不是待接的現成零件。核實過的現況：

- `src/achievements.js` 定義 7 個一次性徽章（純函式 + 獨立 localStorage `thai-review-achievements-v1`）：連續 7 天 / 連續 30 天 / 單日複習 50 張 / 課程全通關 / 全部卡片上手 / 千張複習 / 一週正確率 90%+。
- `src/today.js:134` `buildAchievementCtx()` 組 ctx、`:161` `notifyAchievements()` 跳 toast、`renderAchievementsHtml()` 畫徽章列與「已解鎖 N/7」。
- 觸發點兩處都在跑：`src/today.js:318-319`（進今日 mode 時）與 `src/app.js:262-263`。

所以這一項**不是新功能，是搬視覺**。要做的只有：

- 把徽章列搬進新首頁的版面。
- 該檔用 emoji 當圖示（🔥📅🎓），跟「UI 不放 emoji」的偏好、以及 prototype 的 SVG 線稿風格衝突，**要換成 SVG 線稿**。
- 判定邏輯是 stateless 的，不要改；新首頁只負責組 ctx 和顯示。

### 9.2 進步時刻（新增）

目前所有回饋都在講**量**（練了幾分鐘、複習幾張、來過幾天），沒有一個在講**你變強了**。Duolingo 後期的策略轉向正是這個：從外在獎勵轉成「慶祝小勝利、讓使用者在流利之前就先感覺到自己有能力」。

想達成的效果是偵測「兩週前評過 `again` 的卡，今天答對了」，跳出：

> 「這句你上次不會，現在會了。」

**⚠️ 更正（2026-08-20）**：本節初稿寫「零新資料需求，只是查 `progress` 而已」——**這句是錯的**。核實後：`nextReview()`（`src/srs.js:34-43`）每次評分都回傳一個全新物件覆蓋掉舊的，`progress` 每張卡**只保留最後一次評分**，沒有逐次歷史；`today.js` 的每日日誌也只有當天的聚合計數（`reviewed/again/hard/good/easy`），不是 per-card。所以現有資料**推不出**「以前不會、現在會了」。

**所以要新增一份精簡的卡片評分歷史**。設計要點：

- 只記必要欄位（時間戳 + grade），每張卡保留最近 N 次（例如 5 次）就夠判斷趨勢，不做無上限累積，避免 localStorage 膨脹。
- 跟 `progress` 分開存（獨立 key），不動現有 SRS 結構，避免影響排程計算與既有相容性。
- **排程上的關鍵**：歷史**沒辦法回溯生成**。等到要做這個功能時才加欄位，那時候手上是零筆資料，還要再等好幾週才有東西可顯示。所以**資料結構在 Phase 1 就加、開始默默累積；功能本身 Phase 3 再做**（見第 12 節）。

這種時刻在語言學習特別有感，也是把「累積」變成「成長」的關鍵一步——值得為它多存一點資料。

## 11. 與現有實作的整合（開工前必讀）

這份計畫書前面幾節是照「從零設計」在寫，但**這個 App 已經有一個「今日」mode 了**（2026-06-12 加的第 6 個 mode tab，核心在 `src/today.js`，376 行）。新首頁跟它功能大量重疊，開工前必須先決定怎麼接，否則會養出兩套各自為政的 streak。

### 11.1 現況盤點（已核實）

`src/today.js` 目前同時扮演**資料層**和**畫面層**：

| 角色 | 內容 |
|---|---|
| 資料 | `DAILY_KEY = 'thai-review-daily-v1'` 每日日誌；`loadDailyLog()` / `logReview()` / `initDailyLog()` |
| 資料 | `streakDays()`（`:79`）連續天數 |
| 資料 | `forecastByDay()` / `heatLevel()` 未來到期預測與熱度 |
| 資料 | `buildAchievementCtx()`（`:134`）組成就判定 ctx |
| 畫面 | `notifyAchievements()`（`:161`）、`renderAchievementsHtml()`、`renderTodayMode()`（`:307`）月曆與今日計劃 |

`src/app.js:13` 只 import 了 4 個函式（`initDailyLog` / `logReview` / `buildAchievementCtx` / `notifyAchievements`），耦合面其實很窄——這是好消息。

### 11.2 新首頁跟 today.js 的關係（已拍板：B）

三個選項：

| | 做法 | 評價 |
|---|---|---|
| A | 直接改寫 `today.js`，新首頁取代舊今日 mode | 沒有雙軌問題，但一次動 376 行、月曆和成就都在裡面，風險集中 |
| **B** | **抽出資料層共用，新首頁當新的 view** ← **採用** | `today.js` 保留日誌／streak／預測／ctx 當唯一真相來源，新首頁只消費不複製；舊今日 mode 可以先留著並存，穩了再退位 |
| C | 新開一套獨立日誌與 streak | 最快寫，但保證出現兩套 streak 互相打架，明確不要 |

**已拍板走 B**（2026-08-19），理由跟第 16 節第 6 項（底部導覽列先並存）一致：先並存、驗證、再談取代，符合「重做專案分階段做」的既有教訓。三個關鍵好處：連續天數永遠只有一個數字（streak 是這次養習慣的核心，數字不可信整套就白做）、舊「今日」mode 不動所以新首頁做壞了還有東西可用、風險分次承擔而不是一次賭完。

**已知代價**：短期內 App 會有兩個功能相近的頁面（新首頁 + 舊「今日」mode），視覺上重複。這是刻意接受的暫時狀態，可隨時收掉。

### 11.3 streak 判定要改（第 6 節那條矛盾的解法）

`streakDays()` 現在的判定是 `days[key].reviewed > 0`，而 `reviewed` 只有正式 SRS 評分會加。要讓「完成 1 局就算今天有來」成立，又不能違反第 7 節「遊戲不寫 SRS grade」，建議：

- 每日日誌的 day 物件**加一個 `games` 欄位**，完成一局時 +1（跟 `reviewed` 分開，不混用）。
- `streakDays()` 判定放寬成 `reviewed > 0 || games > 0`。
- **不要**讓遊戲去加 `reviewed`——那個欄位還餵著月曆熱度、`maxDailyReviewed`、`totalReviewed` 三個成就判定，混寫會讓「單日複習 50 張」「千張複習」的語意整個歪掉。
- 舊資料天然相容：以前的 day 沒有 `games` 欄位，`undefined > 0` 是 `false`，不影響既有 streak 計算。

### 11.4 其他要對齊的既有資產

- **成就系統已經接好了**（見 9.1），這次只是搬視覺 + 換 SVG 圖示，不是重接。
- **`prototype-daily.html` 是獨立測試頁**，用自己的 CSS 變數（`--ink` / `--cream` / `--gold`），跟正式 App 的 `styles/base.css`（`--bg` / `--text` / `--gold`）是兩套命名。正式實作要走 `styles/base.css` 那套，不要把 prototype 的變數名帶進去。
- **改動 `src/*.js` 一定要升 `sw.js` 的 `CACHE` 版本號**，否則已安裝的 PWA 完全吃不到更新（這個坑踩過，見專案 README 與記憶）。

## 12. 安全契約（提醒層開工前必讀）

提醒層是這個專案第一次引入「伺服器端長期持有的祕密」與「對外開放的入口」，跟原本純前端 + 唯讀 Sheet 的架構風險等級不同，規則要先定死。

- **祕密只進伺服器 Secret store**：Telegram bot token、VAPID **private** key 一律放 Cloudflare Worker Secrets（或等價的機制），**不進 repo、不進前端 bundle、不進 `data.json`、不寫在 `wrangler.toml` 明文**。VAPID public key 可以進前端，那是設計上就要公開的。
- **不要併進現有 TTS Worker**：`lth-tts-proxy` 持有 GCP TTS key，是目前唯一的付費 API 出口。把推播訂閱與新課事件這些**對外可觸發的入口**塞進同一支 Worker，等於把爆炸半徑從「推播壞掉」放大成「GCP key 也可能被波及、TTS 額度被打爆」。開一支獨立 Worker，各自只持有自己需要的祕密。
- **入口要驗證**：
  - **Push subscription 註冊**：要能確認是本人的裝置，不能是任何人 POST 一個 endpoint 就加進推播名單（否則變成代發垃圾訊息的跳板）。App 本體在 Cloudflare Access 後面，最省事的做法是讓註冊端點也走同一層 Access 保護。
  - **新課事件入口**：由 Sheet 同步流程觸發，屬於機器對機器，要用共享密鑰（header token）驗證，且**只接受觸發、不接受由呼叫端指定推播內容**——內容一律由 Worker 自己去讀 Sheet 組出來，避免變成任意訊息代發。
- **只存必要資料**：推播訂閱只存 endpoint 與金鑰，不存學習內容、不存 `progress`。第一版本來就沒有進度上傳（見 5.3），這條要一直維持到真的決定要做同步為止。
- **可撤銷**：訂閱要能單方面作廢（換裝置、停用提醒）；推播連續失敗（410 Gone）要自動清掉失效訂閱。

### Phase 2：streak 規則 + 跨課連擊局

- **streak 完整規則**：安神保護 2 個、6.1 的結算順序、7 天回補、補救昨天、7 天里程碑、6.2 的月曆顯示。
- **連擊複習（第 2 局）**：跨所有課程的到期／弱卡，最新一堂加權（見第 8 節）。
- 每局結束戰績與重播。
- 局內錯題立即重練。

### Phase 3：對話局 + 進步時刻

- **前置（離線工作，可提早開始，不擋 code）**：AI 生成約 10 組情境對話 → Nalin／老師審核 → 貼進 Sheet 新分頁 → 烤 baked 音檔。素材沒到位就不必動這局的 code。
- **情境對話（第 3 局）**：6 句 3:3、對話完成度、重播整段；資料讀 Sheet 新分頁（C 案，見第 4 節），離線可玩。
- `sync-sheet.py` 與 `data.js` 加對話分頁的欄位對應。
- **進步時刻**：用 Phase 1 起累積的評分歷史，偵測「以前不會、現在會了」。
- **成就徽章搬進新首頁**（系統已接好，只搬視覺 + emoji → SVG 線稿替換，見 9.1）。

### Phase 4：提醒升級與單人便利性

**前提：Phase 0.5 的方向性訊號與 Nalin 自評支持繼續投資**（沒有自動通過的數字門檻，判斷法見 13 節 Phase 0.5），確認提醒真的提高回訪，才值得投資這段工程。

- **Web Push 上線**（CF Worker + VAPID + Cron Trigger），拿到 Android 圖示紅點與一鍵進 App。
- **新課事件通知**：Sheet 同步偵測到新分頁時推播。
- 進度匯出／匯入。

### Phase 5：語音能力（最後）

- 麥克風跟讀。
- 發音或聲音相似度回饋。
- 先做獨立 spike，再決定是否需要付費 AI 或語音辨識服務。

## 14. 明確不做

- 社交、朋友、排行榜。
- 公開 XP、付費寶石、商店。
- 扣心、能量限制、倒數、強迫每日分鐘數。
- 用假的付費貨幣買 streak 補救。
- 純催促、無內容的提醒；一天多則的疲勞轟炸。
- 泛用型 AI 聊天取代課程內容。
- 為了看起來像大 App 而新增複雜的會員和後台。

## 15. 第一版完成條件

「第一版」＝ Phase 0.5 + Phase 1 + Phase 2 交付完畢。要能證明：

1. **每天會主動收到一則提醒，而且提醒裡看得到今天的泰文整句（不是單詞、不是純催促）。**
2. 打開首頁後，一眼知道下一局是什麼。
3. 一次點擊可以開始正確的遊戲局。
4. 完成任一局後，今日挑戰和 streak 正確更新，而且**只做 1 局 streak 就會 +1**。
5. 斷一天之後，安神保護或補救機制真的能把 streak 接回來，而且**不會既扣保護又要求補做**（6.1 的結算順序）。
6. 只玩遊戲沒評分的那天，月曆看得出「有來」，跟 streak 不矛盾（6.2）。
7. 連擊局的題目**跨課程**取到期卡，不是只有最新一堂；連續幾天不會一直抽到同一批卡。
8. 今日只記錄實際累積時間，不設定時間目標。
9. 關掉 App 再打開，自己的進度仍在。
10. 不需要登入、不需要社交，也能完整使用。
11. 評分歷史從 Phase 1 起就在累積（即使「進步時刻」功能還沒上）。

> 生活對話那條（原第 6 點「確實是完整 6 句」）移到 Phase 3 的驗收——資料契約已拍板（第 4 節 C 案），只是這局本來就排在 Phase 3 才做，第一版（Phase 0.5+1+2）驗收不含它。

## 16. Nalin 已確認的決定

1. 「最新一堂」＝最後一堂課程，含總複習，不排除。
2. 遊戲答題結果第一版只記戰績，暫時不直接改 SRS grade。
3. 6 句生活對話固定一人 3 句，不做角色比例例外。
4. `prototype-daily.html` 視覺風格（配色／字體／SVG 線稿圖示）OK，後續遊戲局比照同一套視覺語言。
5. 深色／淺色模式預設要對齊現有 App：預設深色、跟隨系統，可手動切淺色。
6. 手機版底部導覽列先與現有左側 drawer 並存試試看，暫不取代。
7. 「今日一句」內容來源：隨機抽最新一堂課程的一整句，不用單詞。
8. 提醒層（第 5 節）、streak 規則（第 6 節）、成就徽章搬視覺（9.1）、進步時刻（9.2）、新課事件通知（5.3）五項全數納入，Phase 順序照第 13 節調整。
